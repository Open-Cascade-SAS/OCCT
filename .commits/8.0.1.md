## Rules (Required)

The rules follow the established owned-fork practice of the [MS-MPI fork](https://github.com/paulnamalomba/microsoft-mpi-native-windows), `.commits/10.1.4.txt`. See [AGENTS.md](../AGENTS.md#internal-version-and-build-records).

- Format `<breaking>.<major>.<minor>.<build>`. Each of major, minor and build ranges 0 to 9. A successful build increments the fourth field. Carries reset the following fields: `8.0.1.9 -> 8.0.2.0`, `8.0.9.9 -> 8.1.0.0`, `8.9.9.9 -> 9.0.0.0`.
- Failed, cancelled, skipped, configure-only, documentation-only and no-op work does not advance a field.
- The first qualifying build advances the seed to `8.0.1.1`. A build qualifies when the consumer's acceptance builds this fork commit from its pinned archive and passes its required checks.
- Each accepted build adds `.commits/builds/<version>.json` and a record in this note, in the same change as the version bump. The build record holds `accepted`, `status` (`passed`), `source_commit` (the 40-character fork commit that the consumer built), the consumer record that pinned it, checks with results, artifact or archive hashes and remaining limits. This record layout is Proposed; the MS-MPI fork's records use the same three leading fields.
- `.commits/manage-repo.ps1` reads `OCCT_INTERNAL_VERSION` and never changes it. Mutating actions need an attached branch, a clean tree and `-Yes`. Pushes target only `paulnamalomba/OCCT`. Tags use `native/v<internal version>` and are never replaced.
